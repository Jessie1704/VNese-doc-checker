# 01. AI-DLC là gì

## AI-DLC không phải là gì

"AWS AI-DLC" có thể là phương pháp luận hoặc công cụ. Hai thứ này có tài liệu riêng:

| | Phương pháp luận | Công cụ |
| --- | --- | --- |
| Nguồn | Bài blog của AWS | `awslabs/aidlc-workflows` |
| Hình thức | Ba phase, mob programming, bolts | CLI `aidlc` chạy được |
| Trả lời câu hỏi | "Tại sao làm theo cách này" | "Gõ gì, rồi chuyện gì xảy ra" |
| Phân biệt dự án mới / sẵn có | Không | Có, và đây là khái niệm cốt lõi của công cụ |

Playbook này nói về cột bên phải. Nếu bạn cần phần văn hoá làm việc và lập luận nghiệp vụ, hãy đọc bài blog của AWS.

## AI-DLC trong ba câu

1. **Công cụ biến yêu cầu thành phần mềm qua một chuỗi stage cố định.** Bạn mô tả công việc, công cụ chọn một route gồm nhiều stage rồi dẫn bạn qua từng stage theo thứ tự.
2. **Ở mỗi điểm quan trọng, công cụ dừng lại chờ bạn.** Đó là approval gate. Công cụ không tự đi tiếp qua những điểm có hệ quả.
3. **Mọi việc đã xảy ra đều được ghi lại.** Artifact ghi ra file, quyết định ghi vào audit trail, trạng thái ghi vào `aidlc-state.md`. Bạn nghỉ vài hôm rồi quay lại vẫn biết mình đang ở đâu.

## Năm phase

```
INITIALIZATION ──▶ IDEATION ──▶ INCEPTION ──▶ CONSTRUCTION ──▶ OPERATION
 (Khởi tạo)      (Hình thành                  (Xây dựng)       (Vận hành)
                   ý tưởng)
     │                │             │               │               │
  tự chạy,       làm rõ muốn   hiểu bối cảnh,   thiết kế và      triển khai,
  không hỏi      gì, vì sao    chia việc        viết code        quan sát
     │                │             │               │               │
     └───────────┬────┴──────┬──────┴──────┬────────┴───────────────┘
                 ▼           ▼             ▼
        verification gate ở ranh giới giữa các phase
                 │
    OPERATION ───┘ vòng phản hồi quay lại IDEATION
```

Không phải phase nào cũng chạy. Tuỳ workflow profile bạn chọn, một số phase bị bỏ qua. Ví dụ một bản proof of concept không cần phase Operation. Xem [04. Chọn workflow profile](#c-04).

## Stage, route và execute

Mỗi phase gồm nhiều stage. Mỗi stage có một tên định danh thật mà bạn sẽ thấy trong file trạng thái và trong nhật ký, ví dụ `intent-capture`, `reverse-engineering`, `code-generation`.

Hai khái niệm dưới đây hay bị nhầm với nhau:

```
┌─────────────────────────────────────────────────────────────┐
│ TRÊN ROUTE      quyết định lúc bạn CHỌN PROFILE             │
│ (`scopes:`)     stage có tên trong `scopes:` của profile    │
│                 này hay không                               │
├─────────────────────────────────────────────────────────────┤
│ EXECUTE         quyết định lúc CHẠY                         │
│ (`condition:`)  stage trên route chạy thật, hay tự bỏ qua   │
│                 vì điều kiện không thoả                     │
└─────────────────────────────────────────────────────────────┘
```

Stage trên route mà không execute vẫn ghi một receipt `skipped` vào audit. Stage ngoài route thì không xuất hiện trong lần chạy đó.

Ví dụ: câu "dự án mới thì không chạy `reverse-engineering`" đúng ở vế execute, sai ở vế route. Stage này vẫn nằm trên route của gần như mọi profile. Nếu bạn nghĩ nó bị loại khỏi route, bạn sẽ không hiểu vì sao nó xuất hiện trong nhật ký.

Cả hai chiều được liệt kê ở [A.1](#c-a1), tách thành hai bảng riêng.

## Workflow profile

Mỗi workflow profile là một route có sẵn kèm mức độ kiểm soát tương ứng. Ví dụ sửa một lỗi đã biết thì dùng profile `bugfix`, không cần qua stage nghiên cứu thị trường.

Bạn gọi tên profile trực tiếp, hoặc mô tả công việc để công cụ đề xuất:

```
/aidlc mvp
/aidlc Sửa lỗi hết phiên đăng nhập
```

Người dùng gọi là workflow profile, engine gọi là scope và ghi vào `aidlc-state.md`. Danh sách đầy đủ kèm độ nặng của từng profile ở [A.2](#c-a2); cách chọn ở [04](#c-04).

## Agent

Mỗi stage có một agent chủ trì và có thể có agent hỗ trợ. Mỗi agent là một vai chuyên trách: sản phẩm, kiến trúc, lập trình, chất lượng, bảo mật, hạ tầng, vận hành, giao hàng. Ngoài ra còn có vai reviewer và composer (dựng route riêng khi công việc không khớp profile nào có sẵn).

Bạn không gọi agent trực tiếp. Công cụ điều phối chúng theo khai báo của từng stage. Cách các agent phối hợp khác nhau tuỳ stage:

| Kiểu phối hợp | Nghĩa là |
| --- | --- |
| `inline` | Một agent làm, không giao việc ra ngoài |
| `pipeline` | Agent trước xong thì agent sau nhận kết quả, nối tiếp nhau |
| `subagent` | Một agent chủ trì, vài agent kiểm tra độc lập, rồi agent chủ trì tổng hợp |
| `mob` | Nhiều agent cùng đóng góp song song vào một bản nháp |

Kiểu phối hợp quyết định bạn thấy gì ở approval gate. Stage chạy `pipeline` cho bạn xem kết quả của agent cuối cùng, không phải agent đầu tiên.

## Gate: nơi bạn ra quyết định

Công cụ dừng ở hai loại điểm:

- **Approval gate** đặt cuối mỗi stage có hệ quả. Bạn xem artifact vừa tạo rồi duyệt hoặc yêu cầu sửa.
- **Verification gate** đặt ở ranh giới giữa các phase. Câu hỏi ở đây nặng hơn: cả phase vừa rồi đã đủ để đi tiếp chưa.

Mọi bước sau gate đều dựa trên thứ bạn vừa duyệt. Ở phase Inception, duyệt sai một gate sẽ ảnh hưởng tới nhiều stage phía sau trước khi bị phát hiện. Cách đọc một gate ở [15](#c-15).

## Những gì được ghi ra đĩa

```
aidlc/
└── spaces/<space>/              một đội = một space
    ├── memory/                   cách làm việc: org / team / project
    ├── knowledge/                tài liệu bạn đưa vào
    ├── codekb/<repo>/            kết quả phân tích code sẵn có
    └── intents/<mã>-<nhãn>/      một phần việc
        ├── aidlc-state.md        trạng thái: phase, stage, loại dự án, profile
        ├── audit/                audit trail
        ├── ideation/ inception/ construction/ operation/
        └── verification/
```

Hai đường dẫn nên nhớ ngay:

- **`aidlc-state.md`**: muốn biết trạng thái thì đọc thẳng file này. File này là nguồn sự thật; thanh trạng thái chỉ để hiển thị.
- **`codekb/`**: nơi chứa hiểu biết về code sẵn có. Nếu dự án đã có code, đây là thư mục quan trọng nhất và là chủ đề của [11](#c-11).

Cây thư mục đầy đủ theo từng phase ở [A.4](#c-a4).

## Loại dự án: công cụ tự phân loại

Công cụ phân loại dự án của bạn thành greenfield (dự án mới) hoặc brownfield (code base sẵn có). Bạn không khai báo: scanner deterministic tự quyết định ở stage `workspace-detection` và ghi vào `aidlc-state.md`.

Phân loại này quyết định stage `reverse-engineering` có execute hay không, cùng vài điểm khác.

- **Greenfield:** không có code để phân tích, nên stage phân tích code tự bỏ qua. Bù lại, bạn phải dựng lệnh chạy test tối thiểu ở phase Construction, vì chưa có sẵn.
- **Brownfield:** công cụ đọc code của bạn và viết ra một bộ tài liệu mô tả nó. Mọi stage sau đó dựa vào bộ tài liệu này. Nếu bộ tài liệu mô tả sai, mọi stage phía sau sẽ sai theo.

Vì công cụ tự đoán, có ba cách nó đoán nhầm thành dự án mới, và cả ba đều không báo lỗi. Xem [03](#c-03) và [11](#c-11).

Dự án chuyển đổi hệ thống không có loại riêng: công cụ xếp vào brownfield. Xem mục chuyển đổi trong [11](#c-11).

## Harness

Cùng một phương pháp chạy trên nhiều harness: Claude Code, Kiro, Codex, Cursor, opencode, GitHub Copilot. Chỉ khác cách gọi lệnh và nơi đặt cấu hình; stage, agent và gate giống hệt nhau.

Playbook dùng ví dụ dạng `/aidlc ...`. Nếu harness của bạn dùng tiền tố khác, thay tương ứng. Xem [02](#c-02).

## Tóm tắt

| Khái niệm | Ghi nhớ |
| --- | --- |
| Phase | Năm giai đoạn lớn, không phải phase nào cũng chạy |
| Stage | Bước có tên thật, có gate ở cuối |
| Trên route ≠ execute | Nằm trên route mà không execute vẫn ghi receipt |
| Workflow profile | Chọn route và mức độ kiểm soát; engine gọi là scope |
| Agent | Vai chuyên trách, bạn không gọi trực tiếp |
| Gate | Nơi bạn ra quyết định; mọi bước phía sau dựa vào đó |
| Loại dự án | Công cụ tự xác định và có thể xác định sai |
