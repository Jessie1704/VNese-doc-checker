# 03. Pre-flight: biết trước dự án được phân loại thế nào

## Vì sao cần bước này

Công cụ tự quyết định dự án của bạn là greenfield hay brownfield, bạn không khai báo. Quyết định này xảy ra ở stage `workspace-detection`, được ghi vào `aidlc-state.md`, và ảnh hưởng tới toàn bộ phần còn lại.

Lúc stage này chạy, intent và thư mục đã được tạo. Muốn đổi kết quả phân loại sau đó thì phải dọn dẹp thủ công.

```
   BẠN ĐANG Ở ĐÂY
        │
        ▼
  ┌───────────────┐     chỉ đọc, không ghi gì
  │ detect --json │◀─── chạy bao nhiêu lần cũng được
  └───────┬───────┘     không tạo intent, không ghi đĩa
          │
          │ biết trước kết quả, sửa nếu cần
          ▼
  ┌───────────────────────────────────────────┐
  │ /aidlc ...                                │
  │    workspace-scaffold  ← ghi thư mục      │
  │    workspace-detection ← CHỐT loại dự án  │
  │    state-init          ← ghi vào state    │
  └───────────────────────────────────────────┘
          │
          ▼ từ đây, muốn sửa phải dọn dẹp
```

Lệnh này nằm trong mục tham chiếu CLI và được mô tả như một tiện ích nội bộ. Với bạn, đây là lệnh đầu tiên nên chạy.

## Chạy lệnh

Đây là lệnh gọi trực tiếp công cụ, không phải lệnh `/aidlc`:

```
bun .claude/tools/aidlc-utility.ts detect --json
```

Thay `.claude/` bằng thư mục harness của bạn (`.kiro/`, `.codex/`, `.cursor/`, `.opencode/`).

Kết quả gồm:

| Trường | Nghĩa |
| --- | --- |
| Loại dự án | Greenfield hoặc Brownfield; thông tin bạn cần nhất |
| Ngôn ngữ | Ngôn ngữ chính và phụ mà scanner tìm thấy |
| Framework | Framework web, thư viện, bộ công cụ giao diện |
| Hệ thống build | Công cụ build, task runner, package manager |
| Submodule | Các git submodule được khai báo, kèm trạng thái đã khởi tạo hay chưa |
| Thư mục scope | Nơi chứa dữ liệu workflow profile trên harness hiện tại |

Lệnh chỉ đọc: không ghi file, không tạo intent, không ghi audit trail, chạy bao nhiêu lần cũng được.

## Scanner quyết định thế nào

Quy tắc dưới đây lấy từ định nghĩa stage. File này tự khai là nguồn sự thật cho logic phân loại (`core/aidlc-common/stages/initialization/workspace-detection.md:32`).

**Xếp là brownfield nếu có bất kỳ dấu hiệu nào:**

- Có file code thuộc ngôn ngữ được nhận diện
- Có cấu hình framework ứng dụng
- Có package manifest kèm dependency của ứng dụng
- Có thư mục code theo tên quy ước (`src/`, `app/`, `lib/`, `pages/`, `components/`)
- Có `.gitmodules` đọc được với ít nhất một submodule (`core/aidlc-common/stages/initialization/workspace-detection.md:73`)

**Xếp là greenfield chỉ khi tất cả đều đúng:**

- Không có file code nào
- Không có cấu hình framework
- Không có package manifest, hoặc manifest chỉ chứa công cụ phát triển
- Không có thư mục code theo tên quy ước

**Những thứ không làm dự án thành brownfield:** `README`, `.gitignore`, `LICENSE`, cấu hình editor, thư mục rỗng, cấu hình CI/CD không kèm code ứng dụng, thư mục harness và thư mục `aidlc/`.

## Code nằm trong thư mục con

Nếu thư mục gốc không có dấu hiệu nào, scanner đi sâu vào các thư mục con và áp lại cùng bộ dấu hiệu. Nhờ vậy cấu trúc kiểu `services/api/src/main.py` vẫn được nhận ra.

> **Lưu ý:** Hai nguồn đưa ra hai con số khác nhau. Phần hướng dẫn nói scanner đi sâu một cấp (`docs/guide/02-your-first-workflow.md:101`). Định nghĩa stage, vốn tự khai là nguồn sự thật cho logic này, nói giới hạn là ba cấp (`core/aidlc-common/stages/initialization/workspace-detection.md:45`). Khi cần chắc chắn, chạy `detect` và đọc kết quả thay vì suy từ tài liệu.

Scanner gộp ngôn ngữ, framework và hệ thống build của mọi điểm tìm thấy vào kết quả, và không đi sâu hơn một điểm đã tìm thấy.

## Đọc kết quả

### Kết quả khớp mong đợi

Sang [04. Chọn workflow profile](#c-04). Ghi nhớ loại dự án của bạn vì nó quyết định vài nhánh rẽ phía sau.

### Kết quả không khớp mong đợi

Có hai trường hợp sai, cách xử lý khác nhau:

**Bạn có code sẵn, nhưng công cụ xếp là greenfield.** Trường hợp này nguy hiểm hơn vì không có cảnh báo. Stage `reverse-engineering` sẽ không execute, công cụ làm việc mà không đọc code của bạn, và yêu cầu cùng thiết kế phía sau không dựa trên code thật.

Nguyên nhân thường gặp: code nằm sâu hơn mức scanner quét tới; thư mục chỉ có tài liệu và cấu hình; manifest chỉ có dev dependency; hoặc submodule đã khai báo nhưng file `.gitmodules` bị xoá.

Cách xử lý: di chuyển hoặc mở rộng phạm vi trước khi bắt đầu. Chạy `/aidlc` ở đúng thư mục chứa code, hoặc khai báo đúng tập repo làm việc.

**Bạn muốn coi là dự án mới, nhưng công cụ xếp là brownfield.** Trường hợp này ít nguy hiểm và dễ sửa. Tình huống điển hình: bạn vừa dùng một scaffolding tool tạo sẵn cây thư mục, nhưng dự án thực chất vẫn chưa có code.

Cách xử lý: sửa tay `aidlc-state.md`, hoặc dọn sạch rồi chạy lại bước khởi tạo với tuỳ chọn force (`core/aidlc-common/stages/initialization/workspace-detection.md:85`).

## Ba nguyên nhân khiến công cụ coi dự án là greenfield

Scanner chỉ là nguyên nhân thứ nhất. Có ba nguyên nhân dẫn tới cùng một hậu quả (công cụ bỏ qua code của bạn), và cả ba đều không báo lỗi:

| # | Nguyên nhân | Phát hiện bằng |
| --- | --- | --- |
| ① | Scanner phân loại nhầm | `detect --json`, chương này |
| ② | `aidlc-state.md` thiếu trường Project Type, nên mặc định về greenfield | Đọc trực tiếp trường này sau khi khởi tạo, xem [06](#c-06) |
| ③ | Thư mục không phải repo git, nên không tính được fingerprint và rerun guard mất tác dụng | Xem [11](#c-11) |

Nguyên nhân ② nằm ở `core/tools/aidlc-utility.ts:7917`: khi không đọc được trường Project Type, giá trị mặc định là `Greenfield`. Đây là fail open: an toàn cho engine, nhưng với bạn thì toàn bộ bước phân tích code bị bỏ qua mà không có cảnh báo.

Nếu dự án đã có code, hãy kiểm tra đủ cả ba nguyên nhân này.

## Việc nên làm ngay nếu dự án đã có code

```
git status
```

Nếu thư mục chưa phải repo git, chạy `git init` trước khi chạy AI-DLC.

Rerun guard tính fingerprint bằng cách hash nội dung các đường dẫn đã phân tích, và phép hash này dựa vào git. Không có repo git thì không tính được fingerprint, rerun guard trả về trạng thái không xác minh được, và bạn không biết codekb còn khớp với code thật hay không. Chi tiết ở [11](#c-11).

## Kiểm tra trước khi sang chương sau

- [ ] Đã chạy `detect --json` và đọc loại dự án
- [ ] Loại dự án khớp với mong đợi, hoặc đã xử lý chỗ sai lệch
- [ ] Ngôn ngữ và framework được liệt kê đúng với dự án thật
- [ ] Nếu đã có code: thư mục là một repo git
- [ ] Nếu dùng submodule: đã khai báo trong `.gitmodules`

`detect` là cách duy nhất để xem kết quả phân loại trước khi nó được ghi vào `aidlc-state.md`.
